# Отношения и функциональные зависимости

ER-схемы: `01_1NF.md`, `02_2NF.md`, `03_3NF_BCNF.md`.

Правила, из которых берутся зависимости:

- у пользователя два ключа: `id` и `login`;
- у заметки один автор и не больше одного родителя;
- блок можно использовать в нескольких заметках, вложение — в нескольких блоках;
- в одной заметке блок не повторяется, в одном блоке вложение не повторяется;
- `position` уникален внутри родителя;
- `creator_login` и `creator_avatar` — текущие данные автора, не снимок;
- `content` — одно значение, внутри него нет отдельных сущностей;
- прошлая версия блока — отдельная строка: ключ `{block_id, version}`, от одного `block_id` снимок не зависит;
- других нетривиальных зависимостей нет.



## 1НФ

Схема: `01_1NF.md`.

**user** — учётная запись.
**note** — заметка; login и avatar автора пока скопированы в саму заметку.
**favorite** — связь «пользователь избрал заметку».
**note_block_data** — блок внутри заметки: и связь, и данные блока в одной строке.
**block_attachment_data** — вложение внутри блока: и связь, и путь файла в одной строке.

```text
user:
{id} -> login, password_hash, avatar, created_at, updated_at
{login} -> id, password_hash, avatar, created_at, updated_at

note:
{id} -> parent_note_id, created_by, creator_login, creator_avatar, title, header, icon, created_at, updated_at
{created_by} -> creator_login, creator_avatar

favorite:
нет нетривиальных зависимостей

note_block_data:
{note_id, block_id} -> position, content, block_created_at, block_updated_at
{note_id, position} -> block_id, content, block_created_at, block_updated_at
{block_id} -> content, block_created_at, block_updated_at

block_attachment_data:
{block_id, attachment_id} -> position, path
{block_id, position} -> attachment_id, path
{attachment_id} -> path
```

Это 1НФ: в каждой ячейке лежит одно значение, а не список.

Это ещё не 2НФ: данные блока (`content`, даты) стоят в таблице связи и повторяются в каждой заметке, где этот блок используется. Они зависят только от `block_id`, а не от всей пары `{note_id, block_id}`. То же с путём файла: он зависит только от `attachment_id`, а не от `{block_id, attachment_id}`.  

P.S. Для таблицы `block_attachment_data` связи нет, потому что ещё нет уникального родителя для блока. Во 2НФ она появится.

## 2НФ

Схема: `02_2NF.md`.

Данные блока и вложения вынесены в отдельные таблицы. В связях остаются только ключи и порядок.

**block** — содержимое блока.
**attachment** — файл вложения.
**note_block** — вхождение блока в заметку и его `position`.
**block_attachment** — вхождение вложения в блок и его `position`.
`user`, `note`, `favorite` — те же, что в 1НФ.

```text
user:
{id} -> login, password_hash, avatar, created_at, updated_at
{login} -> id, password_hash, avatar, created_at, updated_at

note:
{id} -> parent_note_id, created_by, creator_login, creator_avatar, title, header, icon, created_at, updated_at
{created_by} -> creator_login, creator_avatar

favorite:
нет нетривиальных зависимостей

block:
{id} -> content, created_at, updated_at

note_block:
{note_id, block_id} -> position
{note_id, position} -> block_id

attachment:
{id} -> path

block_attachment:
{block_id, attachment_id} -> position
{block_id, position} -> attachment_id
```

Это 2НФ: неключевой атрибут больше не зависит от части составного ключа. У `note` ключ один — `{id}`, частичных зависимостей у неё и раньше не было.

Это ещё не 3НФ. В `note` есть цепочка `{id} -> created_by` и `{created_by} -> creator_login, creator_avatar`. Автор не ключ заметки: один человек создаёт много заметок. Login и avatar автора — неключевые атрибуты, они зависят от автора, а не от самой заметки.

## 3НФ и НФБК

Схема: `03_3NF_BCNF.md`.

Из `note` убраны `creator_login` и `creator_avatar`. Они живут только в `user`. Отдельная таблица авторов не нужна: это те же `id`, `login`, `avatar`.

**user** — учётная запись; `login` уникален.
**note** — заметка: автор, необязательный родитель, заголовок и оформление.
**favorite** — избранное.
**block** — блок содержимого; может входить в несколько заметок.
**note_block** — какой блок в какой заметке и на каком месте.
**attachment** — вложение.
**block_attachment** — какое вложение в каком блоке и на каком месте.
**block_version** — прошлый снимок блока: номер версии, `content`, кто и когда записал. Текущий текст по-прежнему в `block`.

```text
user:
{id} -> login, password_hash, avatar, created_at, updated_at
{login} -> id, password_hash, avatar, created_at, updated_at

note:
{id} -> parent_note_id, created_by, title, header, icon, created_at, updated_at

favorite:
нет нетривиальных зависимостей

block:
{id} -> content, created_at, updated_at

note_block:
{note_id, block_id} -> position
{note_id, position} -> block_id

attachment:
{id} -> path

block_attachment:
{block_id, attachment_id} -> position
{block_id, position} -> attachment_id

block_version:
{block_id, version} -> content, created_by, created_at
```

Это 3НФ: неключевой атрибут не зависит транзитивно от ключа через другой неключ. В `note` от автора больше ничего не зависит — только ссылка `created_by`.

Это сразу НФБК. НФБК строже 3НФ: левая часть каждой нетривиальной зависимости должна быть ключом. Разница бывает, если часть ключа зависит от того, что само ключом не является. У нас таких зависимостей нет:


| Отношение        | Ключи                                               | Левые части зависимостей       |
| ---------------- | --------------------------------------------------- | ------------------------------ |
| user             | `{id}`, `{login}`                                   | оба ключи                      |
| note             | `{id}`                                              | ключ                           |
| favorite         | `{user_id, note_id}`                                | нетривиальных зависимостей нет |
| block            | `{id}`                                              | ключ                           |
| note_block       | `{note_id, block_id}`, `{note_id, position}`        | оба ключи                      |
| attachment       | `{id}`                                              | ключ                           |
| block_attachment | `{block_id, attachment_id}`, `{block_id, position}` | оба ключи                      |
| block_version    | `{block_id, version}`                               | ключ                           |


Поэтому четвёртая схема не нужна: после 3НФ дробить больше нечего. `block_version` в промежуточные схемы не входил: у него нет частичной или транзитивной зависимости, левая часть сразу ключ.

## Историчность

Историчность ведётся по блокам. Текущий `content` лежит в `block`. Каждое прошлое состояние — строка `block_version`: номер версии, снимок, кто записал (`created_by`) и когда (`created_at`).

## Дополнительные отношения во всех нормальных формах

Таблицы сессий, посещений, участников, приглашений, чатов и сообщений включены
без изменений в схемы 1НФ, 2НФ и 3НФ/НФБК: при следующих зависимостях они уже
соответствуют НФБК. Данные пользователя не копируются в эти отношения.

```text
user_session:
{id} -> user_id, token_hash, created_at, expires_at, last_seen_at, revoked_at
{token_hash} -> id, user_id, created_at, expires_at, last_seen_at, revoked_at

user_visit:
{id} -> session_id, started_at, last_activity_at, ended_at

note_member:
{note_id, user_id} -> role, joined_at, removed_at

note_invitation:
{id} -> note_id, invited_by, invited_user_id, role, status, created_at, expires_at, responded_at

chat:
{id} -> note_id, created_at
{note_id} -> id, created_at

chat_message:
{id} -> chat_id, sender_id, content, created_at, updated_at
```

Перечислены определяющие зависимости; зависимости, следующие из них,
отдельно не перечисляются. Все детерминанты здесь — потенциальные ключи.
Ограничение одного ожидающего приглашения действует только на строки `pending`
и не делает `(note_id, invited_user_id)` ключом всей таблицы `note_invitation`.
Аналогично `session_id` не является ключом `user_visit`: закрытых посещений
одной сессии может быть много.

## Сессии и посещения

**user_session** — сессия авторизации. У пользователя может быть несколько
сессий, например на компьютере и телефоне. Клиент получает случайный секретный
токен, в БД хранится только его хеш `token_hash`. Сессия действует, пока не наступил
`expires_at` и `revoked_at IS NULL`. При выходе заполняется `revoked_at`,
при активности обновляется `last_seen_at`.

**user_visit** — посещение приложения внутри сессии. Оно нужно, чтобы смотреть,
когда пользователь заходит и сколько времени проводит в приложении. Токен может
действовать несколько дней, поэтому срок его действия для этого не подходит.

После 30 минут без активности посещение закрывается: `ended_at` получает время
последней активности `last_activity_at`. Следующая активность начинает новое
посещение. При явном выходе последнее действие тоже учитывается и посещение
закрывается. Тайм-аут проверяет фоновая задача и обработчик новой активности.
Для одной сессии может быть только одно незакрытое посещение; приложение меняет
посещения в транзакции с блокировкой строки сессии.

Длительность оценивается как `last_activity_at - started_at`. Это оценка по
активности, не точное время внимания; для одного действия она равна нулю.
Пересекающиеся посещения одного пользователя на разных устройствах при подсчёте
общего времени объединяются. Время хранится в TIMESTAMPTZ, для статистики по часам
выбирается один часовой пояс. Сессии и посещения не удаляются при выходе;
срок хранения истории задаётся отдельно.

## Участники и приглашения

Под областью заметки понимается одна `note`. Отдельного рабочего пространства
нет, доступ к дочерним заметкам автоматически не наследуется.

**note_member** — кто имеет доступ к заметке. Ключ `{note_id, user_id}`,
связь пользователей и заметок многие ко многим. Роль `editor` разрешает
редактировать заметку, `viewer` — читать. Обе роли могут писать в чат.
Действующие участники — строки, у которых `removed_at IS NULL`.

Владелец — автор из `note.created_by`, он не меняется. При создании заметки
приложение в одной транзакции создаёт заметку, чат и членство автора с ролью
`editor`. Только владелец приглашает пользователей, отзывает приглашения,
меняет роли и удаляет участников. Он не может удалить себя или поменять свою роль.
При удалении участника заполняется `removed_at`. При повторном вступлении оно
обнуляется, а `joined_at` получает новое время. Историю всех повторных вступлений
отдельно не ведём.

**note_invitation** — приглашение зарегистрированного пользователя.
`invited_by` — кто пригласил, `invited_user_id` — кого, `role` — предложенная роль.
Статусы: `pending`, `accepted`, `declined`, `revoked`, `expired`.
`responded_at` заполняется при принятии или отклонении получателем.
Нельзя приглашать себя и действующего участника. Для пары заметка–получатель
может быть только одно приглашение в статусе `pending`.

Принять приглашение может его получатель, пока оно ожидает ответа и не истекло.
В одной транзакции приложение блокирует приглашение, проверяет его, создаёт
или восстанавливает `note_member` и меняет статус на `accepted`.
Если доступ уже получен, повторное приглашение не меняет текущую роль.
Истёкшие приглашения переводятся в `expired` фоновой задачей или перед новым
приглашением: само течение времени не меняет сохранённый статус.

## Чат

**chat** — общий чат заметки, **chat_message** — сообщение в нём.
У каждой заметки один чат. `UNIQUE(note_id)` запрещает второй, а создание первого
вместе с заметкой обеспечивает приложение.

В чате состоят все действующие участники заметки, включая автора. Их может быть
один, двое и больше; фиксированного максимума нет. Личных чатов отдельно нет.
Состав получается через `chat.note_id → note_member.note_id`, где
`removed_at IS NULL`. Поэтому `chat_member` не нужен: он повторял бы эти же данные.
Количество участников вычисляется, отдельно не хранится.

Новый участник видит всю историю чата. После удаления из заметки он теряет доступ,
но его сообщения остаются. Сообщение хранит отправителя, непустой текст и даты.
Перед чтением и отправкой приложение проверяет членство в заметке. Отправитель
берётся из сессии. Редактировать сообщение может его автор, пока он участник.
Проверка доступа и запись выполняются в транзакции с блокировкой членства;
удаление участника использует ту же блокировку. Удаление отдельных сообщений
в этой модели не предусмотрено.

## Ограничения и удаление

БД проверяет ключи, ссылки, допустимые роли и статусы, порядок дат.
Частичные уникальные индексы запрещают два открытых посещения одной сессии
и два ожидающих приглашения одной пары заметка–получатель.
Права, переходы статусов, сроки действия и обязательное создание чата и членства
автора проверяет приложение. Внешние ключи сами по себе этого не обеспечивают.

Удаление заметки удаляет её участников, приглашения, чат и сообщения.
Удаление пользователя удаляет его сессии, посещения, членства и полученные
приглашения, но запрещено, пока на него ссылаются авторство заметки, версии блока,
отправитель сообщения или приглашения. Удаление сессии удаляет её посещения,
поэтому очистка сессий учитывает срок хранения статистики.

## Веб-сокеты

Веб-сокеты используются для обновлений заметки и сообщений её чата.
При подключении проверяются сессия и членство. При удалении участника доставка
данных ему прекращается; при отзыве или истечении сессии нужна новая авторизация.
Веб-сокеты отвечают за доставку, а участники, приглашения и сообщения хранятся в БД.
