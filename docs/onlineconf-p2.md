# OnlineConf: регламенты и расписания

Перед запуском обновлённого backend применяются миграции `000010`, `000011` и `000012`.
Все ручки ниже находятся под `/api/onlineconf/admin`, требуют действующей сессии администратора.
Для POST, PUT и DELETE нужны cookie и заголовок CSRF, как у существующего API ключей.

## Регламенты

- `GET /rollout-plans` — список.
- `POST /rollout-plans` — создание.
- `GET /rollout-plans/{id}` — карточка.
- `PUT /rollout-plans/{id}` — изменение.
- `DELETE /rollout-plans/{id}` — удаление.

Тело создания и изменения:

```json
{"name":"Обычная раскатка","steps":[5,25,50,100],"interval_min":30}
```

Шаги строго возрастают, находятся в диапазоне 0–100 и заканчиваются на 100.
Нужно не менее двух шагов. Пауза — положительное целое число минут.
Используемый регламент нельзя изменить или удалить: `409 ROLLOUT_PLAN_IN_USE`.
Имена уникальны и чувствительны к регистру.

## Привязка и переходы

`PUT /keys/{id}/rollout-plan` принимает:

```json
{"plan_id":"UUID регламента","version":1}
```

Привязка устанавливает первый процент и запускает ожидание следующего этапа.
Значение enabled сохраняется: выключенный флаг включается отдельным изменением ключа.
Для отвязки передаётся явное `"plan_id":null` вместе с текущей версией.
Процент при отвязке сохраняется. Отсутствующий `plan_id` считается ошибкой.

`GET /keys/{id}/rollout` возвращает регламент, текущий индекс `step` (с нуля),
текущий и следующий проценты, `step_ready_at`, `version` и статус:

- `unassigned` — регламент не привязан;
- `waiting` — идёт ожидание следующего этапа;
- `pending_approval` — этап готов, требуется подтверждение;
- `done` — достигнут последний шаг.

`POST /keys/{id}/rollout/approve` и `POST /keys/{id}/rollout/rollback`
принимают `{"version":N}` и возвращают обновлённую карточку ключа.
После каждого изменения нужно использовать новую версию из ответа.
Старая версия даёт `409 VERSION_CONFLICT`.

Approve переводит ровно на один этап и доступен только при `pending_approval`.
Rollback возвращает на один этап и заново запускает паузу. С первого этапа откат невозможен.
После последнего этапа approve недоступен, rollback доступен.

У привязанного флага нельзя менять процент обычным `PUT /keys/{id}`:
возвращается `400 ROLLOUT_STEP_NOT_ALLOWED`. Изменять описание, enabled и
персональные исключения можно. Переходы выполняются под блокировкой строки ключа.

## Расписания

- `GET /keys/{id}/schedules` — список заданий.
- `POST /keys/{id}/schedules` — создание.
- `DELETE /keys/{id}/schedules/{schedule_id}` — отмена ещё не завершённого задания.

Пример тела:

```json
{"run_at":"2099-01-01T12:00:00Z","enabled":false}
```

Нужен хотя бы один из параметров `enabled` и `rollout_percent`.
Значения `false` и `0` учитываются как переданные значения.
`run_at` должен находиться в будущем; время сохраняется как момент времени и передаётся в UTC.

Рабочая задача проверяет сроки каждые 10 секунд. Готовность этапа не изменяет процент:
его увеличивает только подтверждение администратора. Изменения по расписанию, история,
увеличение revision и отметка done записываются одной транзакцией.
Автор изменения — создатель задания. После обработки обновляется снимок сервиса.

Процент по расписанию нельзя изменить у привязанного флага. Правило проверяется
при создании и повторно при выполнении: если после создания задания к флагу
привязали регламент, несовместимое задание получает `failed:true` и текст `error`.
Процент флага при этом сохраняется. Успешное задание получает `done:true`.
Временная ошибка БД откатывает транзакцию; задание остаётся для повторной обработки.

Удаление ключа удаляет его расписания. История уже выполненных изменений остаётся
в `onlineconf_history`, как и для обычного удаления ключа.
